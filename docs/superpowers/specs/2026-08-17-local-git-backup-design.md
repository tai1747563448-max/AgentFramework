# AgentFramework 本地 Git 与备份设计

## 目标

为自有 Agent 框架建立一个独立、本地优先的 Git 仓库，并在 E 盘保存一个 Git 裸备份仓库。工作仓库用于日常编辑；备份仓库只接收 Git 对象和引用，不直接编辑文件。

本设计只覆盖版本管理和备份基础设施。单 Agent、RAG、知识库以及未来多 Agent 的软件架构将单独设计和评审。

## 仓库拓扑

- 工作仓库：`E:\desktop\How_to_build_a_agent\AgentFramework`
- 备份仓库：`E:\GitBackups\AgentFramework.git`
- 工作仓库的备份远程名称：`backup`
- 默认稳定分支：`main`

`E:\desktop\How_to_build_a_agent` 本身不初始化为 Git 仓库。它继续作为多个独立学习项目的容器，避免嵌套仓库被一个总仓库错误吸收。

## 分支模型

早期单人开发只维护两类分支：

- `main`：只保存已经验证、能够解释和能够回退的稳定节点。
- `feat/<topic>`：一次只承担一个边界清晰的功能，例如 `feat/runtime-baseline` 或 `feat/rag-retrieval`。

功能分支通过检查后合并回 `main`。不引入长期 `develop`、`release` 或 `hotfix` 分支，避免在单人早期阶段增加无用管理成本。

## Commit 时机

由 Codex 根据以下规则建议并执行 Commit，同时向用户说明提交原因、文件范围和验证证据：

1. 一个职责单一的变化已经完成。
2. 与该变化相称的构建、测试或文档检查已经通过。
3. Commit 信息能够准确说明本次变化，不混入无关修改。
4. 在高风险重构前，可以在当前功能分支建立明确的检查点；不把未验证状态放入 `main`。
5. 获批的设计文档和实施计划可以各自形成文档 Commit，因为它们是后续工作的可审计决策节点。

建议使用 `docs:`、`feat:`、`test:`、`fix:`、`refactor:`、`chore:` 等清晰前缀，但以内容准确为优先。

## 备份流程

每次创建 Commit 后，将当前分支推送到 `backup`。创建里程碑标签时，同时推送对应标签。备份不依赖自动 Hook，以便每次推送都能被观察、验证和报告。

备份完成的判据是：工作仓库当前分支的 Commit ID 与备份仓库同名分支的 Commit ID 相同。只看到 `git push` 命令启动不算验证完成。

## 安全边界

首个 Commit 前建立 `.gitignore`，默认排除：

- `.env`、私钥和证书；
- CMake、编译器和 IDE 生成物；
- 日志与临时文件；
- 本地知识库数据库、向量索引和 Agent 运行状态。

即使以后连接私有 GitHub，也不得提交密钥。若某份知识库语料确实需要版本管理，必须先确认版权、隐私和体积，再为其建立显式目录及例外规则。

## 恢复方式

工作目录损坏或误删时，可以从 `E:\GitBackups\AgentFramework.git` 重新克隆工作仓库。恢复验证至少包括：能够克隆、默认进入 `main`、Commit ID 一致、受跟踪文件完整。

## 限制

工作仓库和备份仓库位于同一块 E 盘。该备份能够防止误删、错误修改和普通 Git 历史损坏，但不能抵御整块磁盘损坏、丢失或勒索软件同时破坏两个目录。接入 GitHub、另一块物理磁盘或云备份属于后续可选增强。

## 初始验收标准

- 两个目标路径均为有效 Git 仓库，备份仓库为裸仓库。
- 工作仓库默认分支为 `main`，并配置 `backup` 远程。
- 首个 Commit 只包含仓库安全基线和本设计文档。
- 工作仓库保持干净。
- 备份仓库的 `main` 与工作仓库的 `main` 指向同一个 Commit。
- 从备份仓库进行一次临时克隆能够成功恢复首个 Commit。

## 非目标

- 本阶段不连接 GitHub 或其他网络服务。
- 本阶段不复用或搬迁 `D:\Users\Lenovo\AGENT` 的课程代码。
- 本阶段不创建 Agent、RAG、知识摄取、向量检索或多 Agent 的实现文件。
- 本阶段不承诺物理磁盘级灾难恢复。
