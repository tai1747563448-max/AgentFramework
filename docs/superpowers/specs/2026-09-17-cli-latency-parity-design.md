# AgentFramework CLI 延迟对齐设计

日期：2026-09-17。状态：修改计划的设计依据；未开始实施。

用户目标：延迟向 Codex CLI 看齐。用户已确认覆盖完整体验：普通问答和法规查询都要快，分别考核首轮、后续轮和首字延迟。本轮只制定计划，不修改源码、配置、模型、知识包或发布程序，不启动在线基准，不提交 Git。

## 1. 基线与事实边界

当前主工作区 HEAD：`c1f177c`。本机 `codex --version`：`codex-cli 0.153.4`。尚未测量这台机器上 Codex CLI 的交互延迟，因此以下数值是本项目的工程目标，不是 Codex 官方指标。

2026-09-17 对 Ready 的调查记录在 `out/validation/20260917-startup-audit/调查报告.md`：菜单约 7.7 秒，首轮上下文约 173 秒；其中 native 全量验证 130.5 秒，模型阶段 18.3 秒，索引散列 4.2 秒，数据库读取 18.3 秒。独立数据库初始化另一次达到 39.2 秒。普通文本 warm 检索样本 0.927 秒。这是少量样本，不能当作 P50/P95。

首轮样本返回 authoritative_no_match，没有在线模型调用。已有测量没有证明真实命中法规、长对话、在线模型首字或 Codex 对比达标。

官方资料支持以减少串行请求、减少不必要工作、流式输出改善延迟；所查页面没有提供适用于本机的固定 CLI 延迟承诺。不能从官方资料推断 Codex 使用本项目的向量 RAG 或相同后台架构。

- [Codex CLI 官方文档](https://learn.chatgpt.com/docs/codex/cli)
- [OpenAI 延迟优化指南](https://developers.openai.com/api/docs/guides/latency-optimization)

## 2. 目标和计时口径

全部计时使用单调时钟。状态提示不计为模型首字；工具进度不计为回答。等待 RAG、重试、压缩、认证刷新等实际耗时必须进入对应用户路径，不能删掉慢样本。

| 指标 | 起止点 | 计划门槛 |
|---|---|---|
| 菜单可输入 | 启动 EXE → 真正可接受输入 | P50 ≤ 300 ms，P95 ≤ 500 ms |
| 输入确认 | 接受回车 → 显示已接收/真实当前阶段 | P95 ≤ 100 ms；单独记录，不充当提速成果 |
| 普通问答本地准备 | 回车 → HTTP 请求开始发送 | P50 ≤ 200 ms，P95 ≤ 500 ms |
| 法规 warm 准备 | 回车 → 证据已装入模型请求 | P50 ≤ 1 s，P95 ≤ 2 s |
| 法规 process-cold 准备 | 无存活 RAG 进程，立即输入首问 → 请求可发送 | P50 ≤ 3 s，P95 ≤ 5 s；命中与未命中分开统计 |
| 法规 machine-cold 准备 | 重启机器后未预热，立即首问 → 请求可发送 | 最少 5 次独立冷启动，列出全部样本；每次 ≤ 8 s，不用 5 次样本宣称可靠 P95 |
| 首字呈现附加开销 | 收到首个完整、可显示的模型文本事件 → 终端写出 | P95 ≤ 50 ms |
| 取消响应 | Ctrl+C → 前台可重新输入 | P95 ≤ 500 ms；自有子进程回收 ≤ 2 s |
| 后续工具轮本地开销 | 工具结果可用 → 下一模型请求开始 | 不含真实工具执行时间，P95 ≤ 300 ms |

上述是最终目标，特别是未预热语义检索的 5–8 秒属于高风险门槛，必须用真实包证明。不能把 warm 数据代替 cold 数据，也不能用新增“准备完成后才让用户计时”的前置等待规避目标。

在线首字 `TTFT = submit→request_send + request_send→first_text_received + first_text_received→first_text_rendered`。首个 reasoning/status/event 不替代 first_text。另记完整回答时长、输出 token 数、tokens/s、工具轮数、错误率和重试次数。

**Codex 对齐判定：** 在共同任务、固定模型/推理设置及同一时段配对测量中，完整体验首字 P50/P95 目标均不超过 Codex 对应值的 1.2 倍，同时满足上表本地预算。模型不同的结果只作为产品体验差距，不归因于框架；如果当前 MiniMax-M3 的 provider 延迟导致超标，完整对齐状态仍为未达标，不能用“本地已经快了”宣布完成，也不擅自替换用户模型。

若无法为两端配置相同模型/provider，只比较黑盒体验并公开差异；AgentFramework 的净框架开销另用同请求的直连 provider 基线测量。不能用 Codex 的 session/thread 创建事件推断请求已发出。无法观测的边界标为 unavailable，不估造数据。

## 3. 比较三种修改路径

| 路径 | 内容 | 结论 |
|---|---|---|
| A 局部优化 | 线性 JSON、索引覆盖、去掉重复扫描，保持每问原路径 | 必须做，但可能仍受全量 runtime 验证和大模型加载限制，不能单独承诺达到目标 |
| B 完整关键路径改造 | A + 精简可信载荷 + 分层检索/延迟加载 + 任务内证据复用 + 非阻塞记忆维护 + 全链路取消和真实流式计时 | 推荐；覆盖本次完整体验目标 |
| C 跨 EXE 常驻检索服务 | B 上另加每用户进程、IPC、版本协商、访问控制、资源回收 | 暂不作为主方案；不能解决真正 machine-cold，且本机内存有限。只有 B 达到正确性后仍存在明确重启成本，才单独立项 |

执行顺序采用 B，先完成可以独立验证的 A，再逐项加入必要改造。不能通过默认关闭法规库、减少语料、提前无证据生成法规答案、把检索错误改成 no_match 或删除完整性检查达标。

## 4. 目标架构

### 4.1 轻量启动

启动只读取小配置、活动包身份和必要会话投影，先提供可输入界面。未改变的历史不全量回放，不在菜单之前同步调用模型整理记忆。RAG 首问所有实际成本仍计入 cold。

大 JSON 重复键检查改为线性 SAX 校验再构建 DOM，保留大小限制、严格解析、嵌套重复键拒绝和原错误映射。共享适配器只供配置与 RAG 清单使用，不趁机重写所有持久化解析器。

### 4.2 保留信任验证，减少验证对象和重复工作

继续使用原生信任锚验证包身份。新版包将纯 Python 模块和可压缩标准库封装为锁定的只读归档，保留原生扩展/DLL；移除经依赖闭包验证确实不用的 tests、工具链、下载缓存、重复模型后端。不能在已发布包中直接删除文件。

所有实际执行载荷仍在执行前验证 SHA；采用 Windows CNG 流式 SHA-256，复用已经验证并锁定的句柄，减少同一次检查中重复检查祖先路径。保持 reparse/hardlink/额外执行文件检查；缩小可导入路径并阻断环境注入、未声明 `.pth`/sitecustomize/当前目录模块。资源验证、文件句柄及 sidecar 生命周期统一持有。不能仅凭 mtime/文件大小跳过哈希。

模型和索引只验证所用后端的发布集合，不反复验证未使用的另一套后端；同一受保护包实例内复用验证结果。大资产若无法在目标内完成完整验证，保持阻止使用的行为并报告目标未达成，再评估包压缩/后端变化；不引入静默弱校验缓存。

### 4.3 真正按需的法规检索

增加 `retrieval_policy = auto | always | off`，与 `mode = dense | hybrid | lexical` 分离。默认候选为 auto，但只有路由质量门槛通过后才切换发布默认。

- 用户明确要求查法规、存在 CFR 引用、当前会话处于法规问答，或不能确定是否需要法规证据：进入法规检索。
- 只有明确普通问候/语言问题/非法规编程任务才绕过法规库；规则判定不得先增加一次在线模型调用。
- `/rag always` 保留每次查询语义；用户要求“必须查库”覆盖自动路由。`off` 需要用户显式选择，不能自动降级成 off。
- 精确法规引用先查询轻量映射。发布版本保持原 dense 行为作为基准；只有回归证明证据和无匹配语义等价，精确路径才可跳过 dense。
- 无明确引用的语义法规问题必须执行已验收的语义检索；纯词法结果不能在缺乏质量证据时替代 dense，也不能用词法未命中宣称 authoritative_no_match。

sidecar 分为轻量索引就绪、所选编码后端就绪两个阶段。现行 strict v2 ready 不被悄悄改变：采用明确协议 v3，ready 返回 capability；查询需求不满足时等待带截止时间的准备，不能谎报就绪。

模型优先保留 BGE-M3，按真实数据评测模型加载、安全序列化格式、CPU 线程、CUDA 或量化后端。更换后端必须重新建立对应向量索引并通过质量门槛；不同模型/修订/量化版本不混用旧向量。不能把启用 GPU 当成修复 native 校验的方案。

### 4.4 数据库初始化与任务内复用

新包构建时保存 `row_count`、`sum_token_count`，建立覆盖 `(vector_row, chunk_id)` 的索引或紧凑映射文件。运行时读取小元数据和映射，不扫描大文本表计算 AVG。元数据/映射纳入清单散列；发布时全量检查向量行连续、无重复、维度正确。

缓存只保存当前任务内的证据，键包含 task_id、workspace、原查询、包/检索修订、mode、top_k 和字节上限；超时、取消和依赖失败不缓存。包变化、查询变化、显式刷新或任务结束使其失效。工具后问题和包未变则复用，涉及可变外部资料的扩展不能沿用这条规则。

### 4.5 记忆、历史、首字与取消

记忆抽取移出启动/退出/换会话的阻塞路径；显式 remember/forget 仍同步持久化。后台抽取使用独立模型连接和取消令牌，结果由单一写入者检查源序号、忘记事件和 checkpoint 后提交，防止并发覆盖或恢复已忘记记忆。前台请求优先，退出不等待在线抽取；未完成任务下次可恢复。

历史通过版本化本地投影和日志尾增量恢复，JSONL 保持事实来源。仅在测量证明会话量已触发门槛时加入 catalog；不直接合并 Agent_G 的未完成迁移工作。

整个检索操作共享 deadline/cancellation，覆盖 native 验证、Python 启动、模型加载、SQL 和查询；UI 可响应不意味着旧进程可以留在后台继续占用资源。超时、取消、无证据、协议错误必须保持不同结果。

保留现有 SSE 流式通路；校验并显示完整文本事件，不等待整条模型响应。连接复用必须隔离每请求 headers/callback/cancellation，避免过期凭据与跨会话内容串联。长会话压缩耗时单列且计入实际 TTFT；不能截断语义或绕过 hard limit。

## 5. 基准与质量门槛

基准固定 EXE/pack 哈希、CLI 版本、模型、推理强度、输出上限、终端模式、并发数、设备、空闲内存及网络时段。跨产品 prompt/工具权限/证据可用范围一致；Codex 没有等同法规库时给两端相同的只读法规样本，并将“共同资料对比”与 AgentFramework 全库检索性能分开报告。

场景至少包括：普通短问答、非法规编程问题、命中精确引用、缺失精确引用、无引用语义法规问题、中英文同义问、同会话第二问、立即重启首问、长会话压缩、工具往返、检索取消、sidecar 崩溃后重试。

每场景 offline 至少 50 次、online 配对至少 40 次；顺序交错，记录失败样本和 timeout，不仅统计成功最快轮。process-cold 每次回收全部自有 RAG 进程，区分 OS 缓存温热；machine-cold 最少 5 次独立重启，计划不授权当前回合重启机器。

所有法规质量指标以冻结评测集和原版本结果为基线：权威引用正确率 100%；已知缺失引用的拒答正确率 100%；固定集 Recall@5/MRR 不下降；扩展人工标注集 Recall@5 下降不得超过 1 个百分点且 MRR 不下降超过 0.01。自动路由在法规正例集上漏路由数为 0。内容 hash、引用、邻接块及证据禁用工具规则不改变。

进程数、RSS/峰值内存、CPU、读取字节数随延迟一并记录。本机 16 GB 环境总峰值不得超过基线，不得用多份常驻 BGE-M3 换取响应速度。

## 6. 完成条件

只有四项同时满足才能声明“向 Codex CLI 对齐完成”：本地所有性能门槛通过；在线配对体验达到相对门槛；法规质量和安全回归通过；真实 Ready 包在启动、重启和故障恢复上通过。

某一项未达标，则交付明确的阶段改善与剩余差距，不更改验收口径。计划不预先承诺工期或推断每项优化可简单相加；T0 基准后按实际热点重新估计实施成本。
